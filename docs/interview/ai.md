# AI 编程相关

## 在使用 Claude Code 时候的心得和技巧？

考点：实际使用深度，区分「装了没用过」和「重度使用者」。

参考回答：

说几个我觉得最重要的。

最有用的一点是CLAUDE.md一定要写好，但不要写长。我最开始写了200多行的CLAUDE.md，什么代码风格、命名规范、提交格式都写进去了，结果Claude 反而开始忽略某些指令。

后来精简到150 行以内，每条规则自问「删掉这行会导致Claude犯错吗？」不会就删。遵守率明显提高。

最关键的是要写清楚项目的测试命令和lint命令，让Claude 改完代码能自己验证，这一条顶十条风格规范。

在这个基础上，我越用越觉得上下文是最稀缺的资源。我现在的习惯是一个功能点一个会话，做完就/clear。之前吃过亏，一个会话里又改功能又修bug 又加测试，到后面Claude的输出质量明显下降，注意力被之前的对话内容分散了。

复杂任务用Subagent 做调研，比如让子 Agent 去探索某个模块的实现，只把结论带回来，主会话保持干净。

还有就是复杂任务一定要先 Plan 再 Code。我做 MewCode 的多 Agent 协调那块的时候，直接让Claude上手写，结果方向完全跑偏了，删掉重来。后来学乖了，先进Plan Mode让它把相关代码都读一遍，出个方案我看完确认了再动手，一次就对了。

追问：还有没有其他小技巧？

答：几个比较实用的：/btw快速问个不相关的问题不会污染上下文；修了两次还没修对就/clear重新来，写更好的初始prompt 比在烂上下文里挣扎高效得多；用/effort切换思考强度(low/medium/high/xhigh/max)，让模型在复杂问题上花更多时间推理。

追问：你觉得 Claude Code 最大的缺点是什么？

答：终端交互看diff 不方便。改了十几个文件，在终端里一个个看diff 很痛苦，不如Cursor 那种可视化界面直观。我现在的做法是让 Claude 改完后自己 git diff 输出给我看，或者我切到编辑器里用git 插件看。另一个是网络依赖，模型调用全走云端，网络差的时候延迟很高。

## 如何用 AI coding 工具从需求到实现全流程？

考点：对 AI辅助开发完整工作流的掌握。

参考回答：

我觉得主要是三个环节。

首先是把需求聊清楚。不要拿到需求就让AI写代码，这是最常犯的错。我会先开一个会话，把需求描述给Claude，让它反过来问我问题：「这个边界情况你怎么处理？」「这个接口的错误码怎么定义？」「和现有模块怎么交互？」。聊两三轮下来，需求里很多没想清楚的细节就暴露出来了。聊完以后让 Claude整理成一个 spec文件，确认无误再动手。

需求确认了就进 Plan Mode 出方案。让 Claude 读完相关代码后出个实施方案，包含改哪些文件、大概什么思路、有哪些风险点。我看完确认了再退出 PlanMode开始写代码。这一步看似浪费时间，实际上省了大量的返工。我做压缩模块的时候跳过了这步，Claude写了一版方案方向完全不对，改来改去两个小时白费。

方案定了就开始实现。如果需要改大量文件，就用Spec 模式，先让 Claude 生成需求规格和任务拆分，按 SDD(Spec Driven Development)的方式一步步推进，改完一步commit一步。每步完成后让Claude自己跑测试、跑lint，通过了再继续。

关键路径我会再开一个全新会话让Claude 审查，全新上下文没有偏见更容易发现问题，同时频繁commit 保证随时能回滚。

追问：这个流程和不用AI的开发流程区别在哪?

答：最大的区别是反馈循环更快了。传统流程里需求分析、设计、编码、测试是比较线性的。用AI以后，我在第一步就能让 AI帮我做方案推演，相当于写代码之前就「试跑」了一遍。而且迭代速度快，一个小改动从写到测试可能就几分钟，传统可能要半小时。但代价是要花更多精力在审查和引导上，不是省心了而是换了一种劳动方式。

## 你怎么使用 AI 做项目的，全部交给 AI 生成还是每次只提一部分的需求？

考点：对AI辅助开发粒度控制的实际经验。

参考回答：

肯定是分着给的，一次全交不行。

我做 MewCode的时候试过一次「大包大揽」，让 Claude一口气把整个工具系统设计加实现全做了。结果它生成了一大堆代码，接口定义和我预期的不一样，内部状态管理的方式也不对，改起来比从头写还痛苦。从那以后我就不这么干了。

我现在的做法是按任务复杂度分。小活(改个变量名、修个拼写错误、调个格式)直接让 AI做，不需要前戏。中等任务（加个功能、修个bug）给明确的范围，比如「在 tool_registry.go里加一个热插拔接口，参考现有的 Register 方法，加完跑一下测试」。大活(架构调整、新模块设计）一定先聊方案再写代码，先Plan Mode让它读完代码出方案，确认了再实现，每个子任务单独一轮。

关键是一个原则：每次给的任务，小到AI在当前上下文里能完全理解，小到能看完它写的所有代码。如果一次改动超过十个文件都审不过来了，那粒度就太大了。

做MewCode 整个项目下来，我的体感是：AI 最大的价值不是替人写代码，是加速迭代。人定方向、拆任务、审结果，AI负责把想法变成代码。相当于从「打字员」变成了「技术总监」，但技术判断力一点不能少。

追问：你觉得什么时候应该完全不用AI?

答：涉及到关键的架构决策时。比如MewCode选五层架构、权限系统设计多层安全隔离、多 Agent 通信选异步消息模式，这些决策我都是自己想的，不是让 AI 帮我选的。AI可以帮忙做方案推演、列出利弊，但最终拍板必须是人。因为 AI没有对项目全局的理解，它不知道未来三个月要往哪个方向走。
